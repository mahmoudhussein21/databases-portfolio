# Recommendation to Lea Winter and Yasmin Kaya

The daily machine readings and individual write operations should stay in SQLite, while the larger historical reports should use a Parquet copy queried with DuckDB. On this machine, the dashboard report took a median of 1314.41 ms in SQLite and 9.84 ms in DuckDB, and the monthly report took 1446.12 ms and 10.50 ms respectively. The two engines returned matching report groups, with 2,000,000 rows in each dataset. The SQLite history database occupies 107.47 MiB, compared with 2.21 MiB for the first Parquet copy. For the point-lookup workload, SQLite took 0.90 ms for 1,000 lookups versus 133.76 ms in DuckDB, so individual application lookups should not move to the analytical engine. I recommend an automated refresh after the last shift each night, using `refresh.py`, followed by `refresh.py --check` to compare the row count and total price. If that check fails or the refresh is not completed, the reporting page should display the age of the copy and withhold reports that require current data. A matching row count and total price do not prove every row is identical, so additional reconciliation would be needed for a production system.
