# Task 3 — Trigger performance

The test inserts 10,000 vibration readings into a newly created **in-memory** SQLite database. It repeats the same data three times per case in separate fresh databases and reports the median insert time.

Both cases keep the audit trigger, which does no work on new inserts. The only difference is whether the alarm trigger is present. One out of every three readings is above the vibration threshold, so the alarm case produces 3,334 alarm records.

The output is in [trigger_benchmark_results.txt](trigger_benchmark_results.txt), generated by [benchmark_triggers.py](benchmark_triggers.py).

A trigger has a cost because SQLite checks the condition on every inserted row, and for high values it also writes an alarm. A higher time does not mean the trigger is unnecessary: it creates useful safety information automatically. The trade-off depends on how quickly the gateway needs to ingest readings.

These measurements are from SQLite 3.46.1 in the test environment, **not from a Mac measurement**. Running `python3 Module04/benchmark_triggers.py` on macOS will provide local numbers.
